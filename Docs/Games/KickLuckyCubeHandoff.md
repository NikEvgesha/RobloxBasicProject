# Kick Lucky Cube Contributor Handoff

This document is the practical entry point for a developer joining the current Kick Lucky Cube work. The long design and implementation history remains in `Docs/Games/KickLuckyCube.md`; this file explains what to open, what owns each system, what is safe to edit, and how to verify a change.

## Current Checkpoint

- Branch: `develop`.
- Unity editor: `6000.3.9f1`.
- Main scene: `Assets/Games/KickLuckyCube/Scenes/KickLuckyCubeOverview.unity`.
- Status: playable vertical-slice prototype with persistent progression and a broad prefab/UI pass, but not production-ready. The latest manual product review found core-loop, economy, feature-regression, and prefab-ownership work that must be completed before release.
- Primary target: WebGL with desktop and touch controls. Mobile store builds are a later extension.
- Save backend: local `PlayerPrefs` prototype. It is not a production cloud-save implementation.
- Production source of truth: `Docs/Games/KickLuckyCubeProductionBacklog.md`.

Do not treat older smoke-test entries as proof that a feature still works. They are historical checkpoints; current acceptance status belongs in the production backlog and must be confirmed through a fresh Play Mode pass.

The backlog also defines three execution classes: human-owned, agent-owned, and agent-tooling-then-human-finish. Check that assignment before editing a target prefab so Codex and a human do not change the same hierarchy concurrently.

## First Run

1. Switch to `develop` and pull the latest changes.
2. Open the repository root in Unity `6000.3.9f1`.
3. Wait for package resolution and script compilation to finish.
4. Open `KickLuckyCubeOverview.unity`.
5. Check that the Console has no compile errors before entering Play Mode.
6. Enter Play Mode and perform the smoke test in the verification section below.

If local saved data makes a test ambiguous, use `Tools/Kick Lucky Cube/Clear Prototype Save`. This deletes Kick Lucky Cube prototype `PlayerPrefs`; do not use it when the current local progression must be preserved.

## Core Loop

The playable sequence is:

1. Move the player to the kick line; the lucky cube appears in the carry anchor.
2. Start the power selection and confirm the kick with `E` or a pointer click outside UI.
3. The cube flies through the 30-location corridor. Distance uses a non-linear strength curve.
4. A black-silhouette roulette selects an animal from the reached location pool.
5. Control the animal and return to the launch area before the wave catches it.
6. The returned animal enters the inventory/hotbar.
7. Sell it or place it into a player stable slot.
8. Stable animals accrue soft currency in real time, including capped offline time.
9. Spend soft currency on speed, training tools, and stable upgrades.
10. Train strength and use rebirth to reset strength in exchange for a permanent income multiplier.

Supporting loops include rewards, lucky wheel, album discovery, style purchases, weather boost, mob exchange, elite mobs, fake-online ambience, offline earnings, and the 30-day privilege pass prototype.

## Balance and Corridor

The authoritative runtime balance asset is:

```text
Assets/Games/KickLuckyCube/Resources/KickLuckyCube/KickLuckyCubeBalanceConfig.asset
```

`KickLuckyCubeBalanceConfig.cs` provides defaults and calculation methods; the asset contains the values used by the game. Keep code defaults and the asset aligned when introducing a new serialized field.

The corridor is defined by `KickLuckyCubeCorridorLayout`:

```text
LocationCount = 30
FirstLocationStart = 7
LocationSpacing = 48.4
```

The complete 30-location world-design brief, including landmark silhouettes, small props, ambient VFX, exact animal pools, income, and sell values, is `Docs/Games/KickLuckyCubeLocations.md`.

There are 15 regular kick animals and 60 ordered kick variants across Normal, Golden, Diamond, and Fire. Runtime income currently increases linearly by progression index through `KickLuckyCubeBalanceConfig`; grades change tint, VFX, and size rather than applying a second income multiplier. Three former top animals are elite shop exclusives. Keep this documentation and `KickLuckyCubeAnimalGradeUtility` aligned if multiplicative grade income is restored.

Do not independently change scene zone spacing, kick distance conversion, wave tier calculation, and editor decor generation. They all depend on the shared corridor constants.

## UI Authoring Rules

The project is moving from runtime-created UI toward prefab-first authoring. Editable runtime UI assets live under:

```text
Assets/Games/KickLuckyCube/Resources/KickLuckyCube/UI/Templates
Assets/Games/KickLuckyCube/Resources/KickLuckyCube/UI/Elements
```

Use a complete window prefab for each window shell and a separate family prefab for repeated cards or slots. Controllers may update dynamic text, prices, icons, fill values, selected state, visibility, and interactability. Static hierarchy, anchors, spacing, colors, and image sizes belong in prefabs.

Current prefab-first windows include Speed Shop, Strength Tool Shop, Animal Album, Inventory, Sell Shop, Style Shop, Exchange, and Epic Mob Shop. Repeated prefab families include speed upgrades, tool tiers, styles, album cards, sell cards, inventory slots, and epic mobs.

Persistent lower HUD elements belong under `KLC_PrototypeCanvas`. Do not move permanent buttons to the currency FX canvas. TextMeshPro migration is partial: the lower HUD uses TMP, while some older windows still use legacy `UnityEngine.UI.Text`.

Closeable windows should support their close button, `Escape`, and backdrop click unless the interaction intentionally requires confirmation.

## ProBuilder and Scene Authoring

The generated visual layer lives under `KLC_ProBuilderVisuals`. The editor command `Tools/Kick Lucky Cube/Apply World Polish` rebuilds shops, the launch area, corridor accents, biome decor, and the lucky-cube question-mark orientation marker.

Important: generated roots may be replaced by the command. Make durable hand edits in authored prefabs, materials, or the generator code. Do not rely on manual edits inside these roots surviving a rebuild:

```text
KLC_MainLocationProBuilderPolish_v1
KLC_KickCorridorProBuilderPolish_v1
KLC_VoxelPolish_v2
KLC_ProceduralDecor_v2
```

Gameplay triggers and component references should remain on functional scene objects. The ProBuilder layer is primarily visual. Add gameplay colliders deliberately and verify that they do not block the player, animal, cube flight, camera, or interaction raycasts.

Objects prefixed with `MOVE_` are layout handles intended for manual repositioning. Avoid renaming them without checking scripts and documentation for name-based lookup.

## Animal Content Workflow

Runtime animal models and icons are loaded through `KickLuckyCubeAnimalCatalog`. The `.vox` source files are retained under `ArtSource/StealBrainrot/ZooVox`; runtime prefabs remain under the Resources tree.

When adding or replacing an animal:

1. Keep the source model outside the runtime Resources model folder.
2. Create or update the runtime prefab and its `.meta` file.
3. Add the matching icon as a Unity Sprite.
4. Update the catalog entry so model and icon use the same catalog id.
5. Verify silhouette roulette orientation, revealed runner orientation, carry preview, stable placement, album card, and animation fallback.
6. Confirm the animal discovery key is recorded after obtaining it.

Run `Tools > Kick Lucky Cube > Validation > Validate Animal Catalog` before commit. The validator checks all 22 catalog ids, model/icon loads, Animator controllers, and all four grade round-trips. Exchange and shop code must preserve canonical catalog identity; do not append a new display name while reusing an existing catalog id.

Some imported animals use authored animation; `KickLuckyCubeAnimalProceduralMotion` is the fallback for visuals without a usable animation setup.

## Authoring Workspace

Open `Tools > Kick Lucky Cube > Authoring Workspace` for camera-shot preview, connected-prefab extraction, biome corridor preview, world-shop/base contracts, UI state previews, Lucky Cube anchors, and training animation grip tools. Full instructions and safety rules are in `Docs/Games/KickLuckyCubeAuthoringTools.md`.

`KLC_CorridorGameplayData_DoNotDelete` is functional, non-visual scene data. Its 30 trigger-only location zones select the animal progression pool after a kick. `MOVE_KickLine_YellowBar` also owns the player-only corridor boundary. `KLC_ExtendedCorridorFloor_30Zones` is the editable ProBuilder fallback floor and collider for the full kick distance until all biome prefabs provide validated floors. Keep these objects when deleting old blockout decoration; `Install / Repair Tools` can restore them without restoring generated biome art.

Use the workspace instead of the broad legacy `Apply World Polish` command for normal manual editing. `Validate All` reports the exact remaining biome slots, stable-slot bindings, animation contacts, and prefab contract problems.

## Persistence

Prototype persistence uses `PlayerPrefs`. Major key families cover wallet, progression, inventory, stable slots, animal discovery, settings, rewards, styles, wheel cooldown, offline reward timestamps, and privilege-pass state.

Wallet schema uses invariant string-backed `KickLuckyCube.Wallet.Soft64` and `Hard64` values. Old integer `Soft`/`Hard` keys are migrated and deleted after load. Do not reintroduce integer wallet arithmetic or subtract currency outside `TrySpendSoft` / `TrySpendHard`.

Stable slots persist a serialized animal payload, pending soft currency, last real-world timestamp, and upgrade level. Fake-online stable slots must not use the player's persistent slot ids.

Any schema change must provide a sensible fallback for missing keys. Avoid reusing an existing key for a different value type. Before replacing the save backend, keep the current PlayerPrefs adapter behavior available for migration tests.

## Verification Checklist

Run this after gameplay, scene, UI, package, or save changes:

1. Confirm Unity compiles with no Console errors.
2. Start in third person behind the visible player.
3. Move, jump, orbit, and zoom without camera clipping or springing.
4. Enter the kick zone, start the meter, and confirm a kick with both `E` and mouse input.
5. Confirm the held inventory item hides during kick selection.
6. Confirm cube flight, roulette silhouettes, animal/icon match, reveal orientation, and animation.
7. Confirm the wave intro frames the runner and the camera remains in front of the wave.
8. Return successfully, receive the animal, place it in a stable, leave Play Mode, re-enter, and confirm restoration.
9. Confirm real-time/offline income, collection FX, stable pickup, and inventory return.
10. Buy at least one speed level and one training tool; train strength and claim an x2 prompt.
11. Open and close every major window through button, backdrop, and `Escape` where supported.
12. Check desktop and device-simulator UI visibility at a narrow aspect ratio.
13. Run EditMode tests; run PlayMode tests only while the editor is not already in Play Mode.

For a release candidate, also create a WebGL development build and test browser input, persistence, localization glyphs, audio, rewarded-ad fallbacks, and platform commerce capability detection.

## Known Prototype Limits

- PlayerPrefs is local-only and unsuitable for authoritative production economy or cross-device saves.
- Commerce, rewarded ads, and the 30-day pass use prototype adapters/fallback behavior; platform SDK integration still requires a release-specific pass.
- Full UI TextMeshPro migration and full EN/RU localization coverage are not complete.
- The overview scene is large and contains generated visual content, so scene merges are high risk.
- Fake online players and plots are ambience only; they do not represent networking.
- Fake-online runtime actors come from `Resources/KickLuckyCube/World/KLC_FakeOnlineBotActor.prefab`; bot activity anchors live under the plot template and never write player persistence.
- Several systems bootstrap runtime controllers by code. Manager-only bootstrap objects are acceptable, but new visible UI should remain prefab-backed.
- Run the runtime-created visual audit from the Validation menu and consult `Docs/Games/KickLuckyCubeRuntimeVisualAudit.md`; runtime visual migration is clear and new visual or unclassified construction is blocked.
- Generated ProBuilder visuals are a first art pass, not final optimized WebGL geometry.
- `Resources/KickLuckyCube/StealBrainrot/Models/Player/Root.prefab` is a legacy imported skeleton with missing component references. The active runtime player uses `SadovnicOBJ`; do not use `Root.prefab` until it is reimported or repaired.

## Git and Collaboration

Work from `develop` or a short-lived `game/kick-lucky-cube-*` / `fix/*` branch. Keep `master` empty. Before committing:

1. Pull and inspect incoming scene/prefab changes before opening Unity.
2. Keep Unity text serialization enabled.
3. Commit every asset with its `.meta` file.
4. Review changes to `.unity`, `.prefab`, `.asset`, `manifest.json`, and `packages-lock.json` explicitly.
5. Do not commit `Library`, `Temp`, `Logs`, builds, local MCP credentials, or `outputs` workspaces.
6. Update this handoff and the long game document when behavior, workflow, controls, save schema, or package requirements change.

When two people need the same scene, agree on ownership of concrete scene roots before editing. Prefer prefab and ScriptableObject changes over unrelated edits to the main scene.
